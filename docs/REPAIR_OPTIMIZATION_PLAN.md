# AgentGo 修复与性能优化方案

基于 `68714ea` 源码及本轮项目审查整理，日期：2026-10-13。本文是待实施方案，任务均未完成勾选，不表示对应代码已修复。

目标：先保证访问边界和执行结果正确，再解决并发、取消、持久化与索引一致性问题，最后通过测量减少延迟和资源消耗。沿用现有 Go、Redis、PostgreSQL、Milvus 组件，不为本轮修复新增工作流引擎或消息中间件。

## 1. 基线与实施边界

审查证据分为三类：

| 证据 | 已确认内容 | 限制 |
| --- | --- | --- |
| 源码调用链 | Skill 注册变量遮蔽；数据库工具复用应用数据库连接；文档路由未接鉴权；请求选项未完整下传等 | 静态确认，不等于已在真实服务中触发全部后果 |
| 临时诊断用例 | 无凭证时 chat 返回 401，而文档请求进入 Handler 返回 400；取消计入熔断失败；半开连续放行 100 次；流式发送阻塞后取消不能自行退出；Planner 未解析依赖参数并忽略工具业务失败 | 用例用于复现现状，未提交仓库；实施时需写成断言修复后行为的回归测试 |
| 现有测试与历史压测 | 前一轮审查中 `go test ./...` 及核心包 race 测试通过；已有 [Benchmark 结果](BENCHMARK_RESULTS.md) | 外部服务集成测试默认跳过；本轮未测真实 LLM、完整依赖服务及生产负载 |

本方案按以下产品边界落地：

- 文档暂按**共享知识库**处理：认证用户可检索，写入由服务端配置的发布者身份控制。个人长期记忆继续按用户隔离；不顺带实现完整多租户知识库。
- 默认 `agent` 模式继续由 AgentLoop 决策；`planner` 仍需显式选择。Laya 当前仅为影子观测，不承担实际路由，也不能据此声称减少了模型调用。
- 会话保留现有历史与摘要能力；当前 RunState 只存在内存中，本轮不承诺进程崩溃后自动恢复执行，也不自动重放有副作用的工具。
- 兼容性修改覆盖服务端、TUI、测试、示例请求、配置和 benchmark 调用方；不能只改一个函数后即宣布完成。

## 2. 修复位置与优先级

当前主链路如下，方括号对应后文任务：

```text
HTTP / TUI
  → 鉴权与请求校验 [F01、F02、F10]
  → Orchestrator → Harness：会话、Skill、上下文 [F03、F06]
  → AgentLoop / Planner：预算、模型、工具、结果 [F04、F07]
      → LLM Router / Client：熔断与流式传输 [F05、F08]
      → Tool Router → 数据库 / 文件 / RAG [F01、F03]
  → Hook → 会话持久化 → 后台记忆与摘要 [F06]
  → JSON / SSE 返回 [F08]

文档接口 → Importer / ETL → Milvus + PostgreSQL → RAG [F02、F09]
```

P0 是多用户部署前必须关闭的访问缺口；P1 是相关能力用于可靠运行前必须解决的正确性问题；P2 是接口完善及基于测量的性能改进。

| 任务 | 优先级 | 问题与目标 | 完成条件 |
| --- | --- | --- | --- |
| F01 | P0 | SQL / 文件工具的数据访问边界 | 模型生成的参数不能扩大用户和服务端授予的权限 |
| F02 | P0 | 文档鉴权、写入权限与请求体限制 | 未授权请求在调用 ETL 前被拒绝 |
| F03 | P1 | Skill 启动接线与工具定义替换 | 真实启动路径可加载 Skill，工具发现后仍可使用 |
| F04 | P1 | Planner 依赖数据流、失败语义和计划校验 | 下游使用真实上游结果，失败不被包装为成功 |
| F05 | P1 | 熔断错误分类与半开探测 | 用户取消不熔断，半开探测数量有界 |
| F06 | P1 | 同会话并发与消息原子提交 | 同会话轮次不交叉，消息与序号不部分写入 |
| F07 | P1 | 运行期间上下文与资源预算 | 每次模型调用和工具执行都受预算约束 |
| F08 | P1 | SSE 背压、取消与关停 | 下游停止读取后整条生产链可在限定时间内退出 |
| F09 | P1 | ETL 跨存储一致性与任务归属 | 检索只返回已发布版本，多实例不误改他人任务 |
| F10 | P2 | 请求选项、默认配置与文档契约 | 参数实际生效，或在入口明确拒绝 |

## 3. 具体修复任务

### F01：限制数据库与文件工具的权限

**代码范围：** [database.go](../internal/tool/builtin/database.go)、[filesystem.go](../internal/tool/builtin/filesystem.go)、[main.go](../cmd/server/main.go)、[config.go](../internal/config/config.go)、[compose.yaml](../compose.yaml)。

修复前：`database_query` 限制单条 SELECT、只读事务、超时和返回行数，但直接复用应用数据库连接，没有用户或表级访问边界。只读不等于只能读取本人数据。文件工具的可访问范围取决于服务进程权限。

- [x] 数据库工具使用独立连接池与专用只读角色，仅授权明确的业务视图；该角色不得是超级用户或继承应用所有者权限，并核查可通过函数间接越权的授权。禁止访问个人记忆、版本、任务等内部表。未配置工具专用连接时不注册该工具，不回退到应用账号。
- [x] 初期不通过任意 SQL 工具开放个人记忆查询，沿用带用户校验的记忆接口。以后若开放用户私有业务表，再设计服务端身份绑定与数据库行级权限；不能靠模型补 `WHERE user_id`。
- [x] 保留查询超时和行数限制，补充 SQL 长度、单元格及总结果字节限制；日志默认记录查询摘要、耗时与错误类别，避免完整记录敏感 SQL 常量。
- [x] 多用户部署默认关闭文件工具。确需启用时，将读、预览、提交都限制在服务端分配的工作目录内，校验规范化路径及符号链接；请求不得自行扩大目录范围。发布到不可信文件写入环境前还需防止路径检查后的替换竞争。
- [x] 保留 proposal 的所有者、批准 ID 和原内容哈希校验；同一路径的应用内提交需要串行执行“复核哈希 → 替换”，避免两个 proposal 同时通过旧哈希检查。

**当前实现：** 文件工具已默认关闭，启用后按服务端用户身份分配目录，读/搜索/预览/提交都校验目录与符号链接。同路径提交已串行化；实际 I/O 使用用户目录的 `os.Root` 句柄，覆盖路径检查后的符号链接替换竞争，构建要求同步升至 Go 1.25。顶层目录分配仍由服务端管理；共享目录的多实例写入还需要跨进程锁。配置及授权步骤见 [TOOL_PERMISSIONS.md](TOOL_PERMISSIONS.md)。

**验收：** 受限角色真实连接可以查询获准视图，直接查询内部表、通过 JOIN / 子查询读取内部表均失败；返回结果大小有界。文件测试覆盖跨用户 proposal、目录穿越、符号链接逃逸、并发提交与内容已变化。数据库权限测试必须使用受限角色，不能仅模拟 SQL 字符串校验。

**本次验证（2026-10-13）：** `go test ./...`、`go test -race ./internal/tool/... ./internal/config ./cmd/server`、相关包 `go vet` 与 `CGO_ENABLED=0 go build ./cmd/server` 均通过。真实权限测试在临时 PostgreSQL 18.6 中使用独立受限登录角色通过；授权脚本也在隔离数据库执行验证。Docker 当前不可用，未执行 Compose 镜像构建或 PostgreSQL 16 容器验收；其他依赖外部服务的可选集成测试未启用。

### F02：补齐文档鉴权及输入限制

**代码范围：** [router.go](../internal/router/router.go)、[document.go](../internal/handler/document.go)、[chat.go](../internal/handler/chat.go)、[TUI](../cmd/tui/main.go)、[seed.sh](../benchmarks/seed.sh)。

- [x] 将上传、异步导入、状态查询接入现有认证中间件；OIDC 开启时，缺失或无效凭证统一返回 401。
- [x] 共享知识库的上传与覆盖要求命中服务端发布者身份白名单；已认证但无写权限返回 403。默认空白名单不开放远程写入；本地模式显式保留 `local-user` 的开发入口。
- [x] TUI 的文档上传、导入和状态轮询统一携带现有会话使用的 Authorization；同步更新种子脚本、benchmark 和接口示例。
- [x] JSON 上传与 chat 在解析前设置请求体上限；文档文本、文件和元数据分别限制大小，超限返回 413。沿用已有文档大小配置或常量，避免 JSON 路径绕过 multipart 限制。
- [x] 当前文档 ID 由类型与标题生成：保持共享文档语义，覆盖时要求匹配预期版本或内容哈希，冲突返回 409。不要仅在 ID 中添加 user_id 就声称完成私有知识库隔离。

**验收：** 无凭证 401、无发布权限 403、合法发布者成功；覆盖冲突和超限请求不调用 ETL。认证开启后，TUI 上传与轮询端到端可用。公开健康检查和指标接口的暴露范围由部署配置单独管理。

### F03：恢复 Skill 完整调用链

**代码范围：** [main.go](../cmd/server/main.go)、[harness.go](../internal/harness/harness.go)、[loop.go](../internal/agentloop/loop.go)、[skill](../internal/skill)。

- [ ] 消除 `skillRegistry, diagnostics := skill.Load(...)` 对外层变量的遮蔽，让同一个 Registry 同时接入 `load_skill` 与 Harness。
- [ ] 调整 `replaceBusinessTools`：替换业务工具时保留获准的 `list_tools`、`load_skill` 等控制定义及本轮必要工具，并去重；不能绕过 scope 和显式禁用设置。
- [ ] 增加启动装配测试，使用临时 Skill 目录走真实装配逻辑；避免只在 Harness 测试里手工 `SetSkills`。

**验收：** 显式选择 Skill 成功，自动发现可用；“发现业务工具 → 加载 Skill”成功；`skills: []` 禁用且不会在后续工具替换中重新出现；不存在的 Skill 明确报错。文档只承诺当前支持的 Skill 提示内容，不把未实现的脚本执行写成已有能力。

### F04：修复 Planner 的依赖与结果语义

**代码范围：** [planner.go](../internal/agent/planner.go)、[Tool Router](../internal/tool/router.go)、[模型结构](../internal/model/request.go)。依赖 F07 的预算控制。

现状：`depends_on` 只检查前序编号是否存在，预先生成的工具参数不会获得真实结果；`ToolResult.Success=false` 会被忽略；无工具步骤直接把描述当作输出。

- [ ] 执行任何工具前校验整份计划：步骤上限、唯一 ID、依赖存在性、无环、工具在授权且已选择集合内、参数结构有效。先实现稳定的拓扑顺序串行执行，不增加并行 DAG 调度器。
- [ ] 采用运行时参数生成：有依赖的步骤将任务、步骤描述、真实依赖结果和唯一允许工具的 Schema 交给现有模型调用，取得参数后再次校验并执行。无依赖步骤可直接使用校验后的计划参数。不引入 `$step1` 一类未定义的字符串替换协议。
- [ ] 无工具步骤执行受预算限制的模型推理，不能直接返回步骤描述。新增模型调用纳入耗时、usage、取消和总调用次数统计。
- [ ] 统一处理 Go error、空结果及 `Success=false`，记录成功、失败、阻塞状态。失败步骤的依赖步骤不执行，最终返回已完成部分及明确失败原因；有副作用的步骤不自动重试。
- [ ] 汇总按确定顺序输入结果，保留原始用户约束和必要 Skill 指令，将检索及工具输出作为不可信数据；禁止把失败结果描述成已经完成的动作。

**验收：** “查询数值 → 根据结果计算”第二步收到第一步真实值；业务失败能够阻断后继；重复 ID、环、缺失依赖、超长计划在首个工具执行前失败；无工具步骤有真实推理结果。现有独立步骤任务行为保持兼容，新增模型开销单独量化。

### F05：修复共享熔断与探测放行

**代码范围：** [LLM Router](../internal/llm/router.go)、[circuit_breaker.go](../internal/llm/circuit_breaker.go)、[client.go](../internal/llm/client.go)、[extractor.go](../internal/memory/extractor.go)。

- [ ] 区分用户取消、调用方预算超时、无效请求与上游服务故障。前几类不记为供应商健康失败；429、5xx、连接失败及供应商调用超时按明确策略计入。使用可识别的错误来源，不能把所有 deadline 都判为同一种故障。
- [ ] 半开状态用有限探测许可控制并发；取消、成功、失败均释放许可，避免重复获取。携带探测代次，防止较早请求的迟到结果污染新一轮状态。
- [ ] 为前台 Agent 与后台提取、摘要、重排序区分容量和预算，保留真实供应商故障的共享健康信号。单纯把后台超时从 10 秒调到 60 秒只属于临时缓解。
- [ ] 明确 SDK 重试与 Router failover 的总尝试次数、总时限。允许在尚未产生可见响应时进行有限备用模型尝试；已经发送部分流内容时返回终止错误，不拼接另一模型的回答，也不重放整条工具链。

**验收：** 连续取消和后台自身预算到期不打开主模型熔断；真实上游失败仍可熔断；并发半开探测不超过配置许可数；许可在取消后恢复，迟到响应不错误关闭新熔断；HTTP 与 SSE 使用相同错误分类。

### F06：保证会话轮次与消息提交一致

**代码范围：** [harness.go](../internal/harness/harness.go)、[session.go](../internal/memory/session.go)、[redis.go](../internal/cache/redis.go)、[compactor.go](../internal/agentcontext/compactor.go)。

- [ ] 在读取上下文前取得会话执行权，持有至消息提交结束；同会话并发请求先采用明确返回 409 的策略，避免无限排队。多实例使用 Redis 所有者令牌、续租与条件释放；失去执行权立即取消本轮，并在继续工具执行与消息提交前检查所有权。
- [ ] 新增轮次提交接口，通过 Redis Lua 将用户消息、助手消息、连续序号、TTL 和 run_id 去重记录一次提交；先完成参数、键类型等校验再写入。原有单消息调用方一并迁移，避免保留另一条非原子写入路径。
- [ ] 相同 run_id 的提交重试不重复写消息。该能力只保证持久化提交幂等，不代表整个 Agent 或外部工具可安全重放；执行权失效也不能撤销已发出的外部副作用。
- [ ] 持久化失败向调用方返回明确的存储失败状态与 run_id，保留已完成结果及可能已执行的工具信息；不能只记 warning 后返回普通成功，也不能提示客户端无条件重试整轮。
- [ ] 识别历史已存在的序号缺口，为摘要增加可观测的修复/重建路径，避免永远卡在缺口。后台记忆提交失败记录独立指标；采用有界提交预算，但仍明确 Redis 消息与 PostgreSQL 任务之间不是原子事务。

**验收：** 同会话只允许一个在途轮次，不同会话可并行；模拟超时重试、Redis 写失败、租约丢失及进程退出，验证不产生半对消息或重复提交。摘要能识别旧缺口。记忆提取暂保持尽力提交；如要求必达，另立持久化待投递记录及幂等消费任务，不伪称当前已经保证。

### F07：补齐每次调用前的预算控制

**代码范围：** [builder.go](../internal/agentcontext/builder.go)、[loop.go](../internal/agentloop/loop.go)、[planner.go](../internal/agent/planner.go)、[tool/router.go](../internal/tool/router.go)、各内置工具。

初始 Context Builder 已有估算和裁剪；缺口主要在后续持续追加的工具结果、工具参数与新增定义。

- [ ] 在每次 LLM 调用前重新计算 messages、system、tool-call 参数及 Schema，预留输出 token；预算受所选模型能力和用户 max_tokens 共同约束。
- [ ] 优先裁剪低价值记忆与旧历史，保留必要用户约束；assistant tool-call 与其 tool-result 成组保留或删除，不能制造无配对消息。最小必要上下文仍超限时明确失败。
- [ ] 工具在生成或读取输出时限制总字节，避免先把大文件或大单元格全部读入内存再截断；模型输入和客户端事件分别设置限额，返回有效 JSON 和截断标记。
- [ ] 限制每轮工具数、总工具数、Planner 步数、模型调用次数及任务时限；工具发现调用、修复参数调用也消耗预算。
- [ ] 增加有界并发准入及供应商容量限制；过载在发送 SSE 响应头之前返回明确状态，不允许等待队列无限增长。

**验收：** 长历史、超大工具结果、同轮大量工具调用、多步 Planner 都能在限额内完成或明确终止；不会将超限请求继续发给模型。截断后协议和 JSON 仍有效，必要审批信息与 Skill 约束仍保留。

### F08：贯通 SSE 取消与关停

**代码范围：** [client.go](../internal/llm/client.go)、[LLM Router](../internal/llm/router.go)、[chat.go](../internal/handler/chat.go)、[TUI](../cmd/tui/main.go)、[main.go](../cmd/server/main.go)。

- [ ] 所有流式 channel 发送与等待都可响应 context 取消；明确 producer 负责关闭自己的 channel，consumer 停止读取时取消整条上游链。
- [ ] SSE 写入错误、flush 错误或写期限到达时取消 Run；设置有界的写等待，不以无限缓冲隐藏慢客户端。
- [ ] TUI 停止、切换会话和退出时取消原流；旧生产者不会永久阻塞在无人消费的事件队列。工具事件大小与 TUI scanner 上限使用一致契约。
- [ ] 区分中间阶段增量和最终回答；明确成功、失败、取消的终止事件，客户端不把已显示的部分内容当作执行完成。连接可写时终止事件至多一次。
- [ ] 对齐 HTTP 写期限、Agent 时限和关停预算；先停止准入，再等待或取消在途任务及后台 worker，最后关闭依赖连接。

**验收：** 使用受控模型流和真实 HTTP 客户端覆盖慢读、断连、填满 buffer 后取消、TUI 停止、服务关停。所有相关 goroutine 在测试期限内退出；正常流内容完整，终止状态准确，取消不计入供应商故障。

### F09：按文档版本发布索引

**代码范围：** [pipeline.go](../internal/etl/pipeline.go)、[importer.go](../internal/etl/importer.go)、[postgres.go](../internal/database/postgres.go)、[retriever.go](../internal/rag/retriever.go)、[vectordb](../internal/vectordb)。

现状：先写向量、删除旧向量，再写 PostgreSQL；失败时两侧可不一致。同步上传和异步导入的状态处理不同，启动时统一标记 processing 任务失败也不适用于多实例。

- [ ] 先统一同步与异步导入的任务状态，区分“当前导入任务失败”和“上一已发布版本仍可用”；不能靠统一标记 processing 就宣称解决跨库原子性。
- [ ] 为逻辑文档引入 generation；chunk ID、向量元数据和关键词记录携带版本。新版本独立构建，不提前覆盖或删除旧版。
- [ ] 向量写入且满足读取可见条件后，在 PostgreSQL 事务内提交关键词版本和 active_generation；检索两路均只使用已发布版本。Milvus 候选做版本校验并有界补召回，避免未发布候选挤占 top-K。
- [ ] 发布成功后异步清理旧版；失败可按相同任务/版本幂等重试并清理孤儿数据。清理必须避开当前活动版本、回滚保留版本和仍在读取的版本。
- [ ] 导入任务记录持有者、租约和尝试次数，启动恢复只处理租约过期任务。若提供崩溃恢复，原始输入也必须持久化，并复用现有 PostgreSQL 任务领取模式；仅本机临时文件加内存队列不能承诺恢复。

**验收：** 在向量写入、关键词提交、版本发布和旧版清理各点注入失败；每次检索仅使用同一已发布版本，旧版可继续查询，重试不产生重复可见记录。两个实例导入时不会把对方在途任务误判为失败。完成该项后再提高导入并发。

### F10：让参数与配置契约一致

**代码范围：** [request.go](../internal/model/request.go)、[orchestrator.go](../internal/agent/orchestrator.go)、Harness、AgentLoop、Planner、[config.go](../internal/config/config.go)、[config.yaml](../config.yaml)、[.env.example](../.env.example)、[compose.yaml](../compose.yaml)。

- [ ] 将 model、temperature、max_tokens 下传到本轮前台执行链，明确辅助提取、摘要、重排仍使用各自默认策略。不存在或不支持请求能力的模型在入口拒绝。
- [ ] temperature 使用可区分“未提供”和显式 0 的表示；同步修正 JSON 解码、TUI、测试构造和示例，避免零值又被默认值覆盖。
- [ ] `enable_rag=false` 从本轮工具能力中移除 knowledge_search，并在执行权限层再次限制；true 不突破显式 tools 白名单，也不表示每次都强制检索。
- [ ] 明确 `/chat` 与 `/chat/stream` 决定传输方式，对冲突的 stream 字段给出确定行为；梳理只被旧执行路径使用的配置，不让用户误以为已影响 Harness。
- [ ] 对齐代码默认值、YAML、环境变量模板和 Compose 中的 reflection、timeout 等设置，增加无环境变量干扰的默认配置测试。

**验收：** 表驱动测试覆盖每个选项的缺省、显式值、非法值，以及 agent/planner 两种模式；断言下游实际请求和工具权限，而不只检查结构体字段。

## 4. 性能优化任务：先测量，再选择

以下是源码暴露的优化候选；除非完成对照实验，不承诺提速百分比或并发容量。每项单独提交，先满足前述正确性约束。

| 任务 | 源码依据 / 优化方向 | 实施方案与前置条件 | 验收指标 |
| --- | --- | --- | --- |
| P01：建立可比较基线 | 现有 Prometheus、Trace 与 benchmark 已可复用 | 按对话、RAG、依赖工具、长历史、Planner、导入分类；区分前台/后台、逻辑调用/SDK 尝试；记录缺失 usage 比例，不当作零成本 | TTFT、端到端 P50/P95/P99、成功率、工具/检索正确率、tokens、排队时间、goroutine、RSS；指标标签不含 user_id、session_id 或原文 |
| P02：减少工具发现往返 | [manager.go](../internal/tool/manager.go) 与 Loop 的 catalog/load 流程 | 对小工具集比较“直接提供必要 Schema”与当前惰性加载；大集合继续按需加载。先完成 F03，所有方案保留权限过滤 | 固定任务下模型调用次数、输入 token、TTFT 和成功率；不能以少调用但漏选工具判为优化 |
| P03：减少记忆 / RAG 的串行查询 | [managed.go](../internal/memory/managed.go)、[retriever.go](../internal/rag/retriever.go) 的逐候选回查 | 按候选 ID 批量读取记忆/文档状态，带用户、有效期与版本过滤；相同文档去重查询。语义记忆检索设置独立可选路径预算，超时可退回当前会话上下文 | SQL 次数随批次数增长而非逐候选增长；召回与隔离正确；embedding 慢时首响应仍有界 |
| P04：收敛历史读取与全局锁 | [session.go](../internal/memory/session.go) 全历史读取；[manager.go](../internal/tool/manager.go) 持全局锁执行 Redis I/O | F06 后按摘要水位分页加载必要历史，先减少读取而不删除原始历史；工具统计用 Redis 原子增量/批处理，缩短进程锁范围，保持跨实例计数一致 | 1k/10k 消息会话的读取字节、分配、耗时；不同会话并发时锁等待和 Redis 往返；摘要所需历史不缺失 |
| P05：改善索引与后台吞吐 | [postgres.go](../internal/database/postgres.go) 逐 term 插入和每次语料统计；[jobs.go](../internal/memory/jobs.go) 定时单任务领取；ETL 全局锁 | 先批量写入 term；有队列任务时持续有界领取，空队列再退避。F09 后按文档限制并发，分批 embedding/upsert；只有分析证实语料统计昂贵时才维护预聚合统计 | 导入 chunks/s、峰值内存、队列最老年龄、任务吞吐、前台 P95；后台增长不能挤占前台容量 |
| P06：约束 Laya 影子开销 | [laya.go](../internal/intent/laya.go)、[harness.go](../internal/harness/harness.go)、Planner 影子调用 | 当前已有 HTTP 超时，但每次请求启动的影子 goroutine 缺少全局并发上限；增加有界并发、采样及独立关停。离线验证前保持 shadow，不直接切 live | 影子排队/丢弃/错误率、主链路 P95；意图与工具选择准确率、拒答率，按置信度分桶，未知/低置信度可回退 |

可选的第二轮优化：

- **Embedding 缓存：** 先测重复查询比例；命中率足够时再做有界缓存及请求合并。key 包含模型、维度、文本规范化版本与文本摘要；缓存向量不等于缓存跨用户检索结果，故障时应能降级。
- **重排质量与成本：** 将候选数量与最终 top-K 分开配置，评估当前截断内容对相关性的影响；对比关闭重排、不同候选数量的效果与延迟。没有质量收益时避免额外模型调用。
- **SSE / TUI 渲染：** 先通过 profile 判断小事件写入、字符串累计和全量重绘占比，再考虑合并小增量与限制可视日志；不得明显延后首个增量。
- **连接池：** 依据池等待、数据库 CPU 和慢查询调整，避免只提高 PostgreSQL/Milvus 并发使尾延迟恶化。F01 的工具连接与内部持久化连接分别观察。

## 5. 推荐实施顺序与拆分

按以下顺序形成可独立审查的变更，不把安全修复、协议变更和性能实验塞进同一提交：

1. **基线与访问边界：** P01 记录现状；F01、F02 分别落地。多用户服务上线必须先通过这两项。
2. **小范围功能修复：** F03 → F05 → F10。分别验证真实启动装配、故障分类和请求参数契约。
3. **运行稳定性：** F07 → F04；F06 与 F08 分开实施并进行联合回归。Planner 的新模型调用统一受 F07 约束；客户端同步适配 F06/F08 的终止状态。
4. **索引一致性：** F09 先完成迁移与故障注入验证，再开放多个导入 worker 或多个服务实例共同导入。
5. **性能对照实验：** P02、P03、P04、P05、P06 按基线暴露的瓶颈排序，逐项测量。未达收益或损害质量的改动撤回，不继续堆配置。

每项完成时记录：关联提交、配置/协议变更、回归测试、测量报告、已知限制；然后再勾选本文任务。工期取决于数据库迁移及服务联调结果，不把静态估计作为交付承诺。

## 6. 迁移、发布与回滚

| 变更 | 发布步骤 | 回滚边界 |
| --- | --- | --- |
| SQL 工具权限 | 先创建最小权限角色和视图，验证授权；配置独立连接，再切换工具注册 | 回滚时关闭工具；不能恢复使用应用高权限账号 |
| 文档鉴权 | 更新客户端凭证传递、发布者配置与种子脚本，再部署受保护路由 | 保留鉴权；旧客户端不能用恢复匿名写入来兼容 |
| 会话原子提交 | 新版本兼容读取旧消息格式；发布前停止旧版接收新轮次并排空，避免新旧写路径同时写同会话；盘点旧序号缺口 | 保留现有消息与序号，只在停止写入后回退；不要删除用户历史以掩盖缺口 |
| ETL generation | 先增加字段及兼容读取；暂停导入，保留快照，对已有向量/关键词分批回填初始 generation 并核对；切换版本写入与读取后恢复导入 | 保留旧版数据至回滚窗口结束；新版本发布后不能直接启动不了解 generation 的旧代码，必要时停写并恢复对应快照/兼容版本 |
| 性能优化 | 固定同一数据集、配置和模型版本进行前后对照；每轮只改变一个主要因素 | 优先回退该项代码/配置，保留报告；不得绕过权限、版本过滤或错误检查维持性能数字 |

ETL 的 active_generation 发布必须考虑 Milvus 的读取可见性，并让单次检索使用一致的已发布版本集合。跨库无法依靠 PostgreSQL 单个事务完成原子写入，方案依靠版本隔离、发布指针、重试和清理实现可见结果的一致性。

## 7. 验证计划与发布门槛

### 7.1 自动化回归

在仓库根目录执行；这些是后续实施的验证命令，本次文档变更不代表重新执行了全部检查：

```bash
go test ./...
go test -race ./internal/harness ./internal/agentloop ./internal/agent ./internal/tool/... ./internal/agentcontext ./internal/memory ./internal/llm ./internal/etl ./internal/intent ./internal/laya
go vet ./...
```

此外，每项修复在对应测试包增加其验收用例，重点是启动接线、真实调用链和故障结果。常规全量测试通过不能替代数据库权限、跨存储版本或 HTTP 断连测试。

### 7.2 依赖服务集成

使用独立测试数据库、Redis 命名空间及 Milvus collection，配置好测试连接后执行现有集成测试：

```bash
POSTGRES_INTEGRATION=1 go test -count=1 ./internal/database ./internal/memory
POSTGRES_INTEGRATION=1 MILVUS_INTEGRATION=1 go test -count=1 ./internal/database ./internal/memory ./internal/vectordb
```

新增集成场景还需覆盖：F01 受限数据库角色、F06 Redis 原子提交与租约、F09 双实例导入及各阶段故障。Redis/Milvus/PostgreSQL 断连和恢复后验证数据内容与状态，不能只看请求是否返回 200。

### 7.3 压测与质量评估

沿用 [Benchmark 文档](BENCHMARK.md) 的工具与报告格式，先把示例数据整理为人工核对、固定版本的评测集。至少覆盖普通对话、单工具、依赖工具、多轮记忆、RAG、Planner、长上下文和错误恢复。

- 固定模型桩测试服务开销、背压、并发和故障；真实模型测试质量、TTFT、成本及供应商行为，两类结果分开报告。
- 分别比较新会话、长会话、不同用户并发和同会话冲突；导入及记忆后台任务关闭/开启各测一档。
- 并发逐级上升，记录持续时间、样本量、完成率、排队长度及资源曲线；短时成功不等于稳定容量。P99 样本不足时明确标注。
- 硬门槛：越权测试全部拒绝；Planner 不掩盖失败；数据不部分提交；取消后无持续累积的 goroutine；索引不混用未发布版本。
- 性能门槛：先登记基线和质量容差，再约定每项优化的目标；目标值由真实数据确定。只有延迟/资源收益可重复且质量达标才保留优化。

首批建议交付 F01、F02、F03、F05：优先关闭访问缺口，修复可明确复现的功能与稳定性问题，再推进涉及协议和数据迁移的工作。
